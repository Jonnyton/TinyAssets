**2. Is CIMD enablement + registration recreation the smallest justified next mutation?** Yes. ## Findings by severity

**M1 (medium) — the `oauth_rejection_categories=[]` detector has no live positive control, and two artifacts overclaim it.** The sanitizer's envelope matcher is unit-tested and was independently review-hardened, but no production window has ever shown a *nonzero* category. That makes tasks.md 1.2's "**proving** these attempts stopped before the instrumented bearer validator" and user_sim's "Neither attempt **reached** the instrumented TinyAssets bearer validator" stronger than the evidence. The boundary conclusion still stands on the rendered evidence, but these two sentences treat the weakest corroborant as proof.

**L1 (low) — attribution confound on success.** The experiment changes two variables at once (CIMD advertisement + fresh registration). If continuity is restored, the audit should record that success does not attribute cause between "fresh registration" and "CIMD mechanism" — the real acceptance remains the immediate + later-refreshed call sequence and restart survival, plus the task 3.3 monitoring row.

**L2 (low) — normalization asymmetry in the check.** `check_discovery_contract` rstrips the expected resource but compares the advertised `resource` raw, so a semantically-equal trailing-slash advertisement would false-fail as `resource_mismatch`. Live matches exactly today; fix opportunistically.

**L3 (low) — stricter-than-RFC pinning.** `bearer_methods_supported`, `grant_types_supported`, and `token_endpoint_auth_methods_supported` are optional with defined defaults under RFC 9728/8414, but the check requires explicit advertisement. As a deployment-drift contract pinned to the actual live documents this is defensible — keep it, but it is a deliberate choice worth a one-line comment so a future reader doesn't "fix" it as a bug, and it means the check is a TinyAssets contract, not a generic RFC validator.

**L4 (low) — no discovery-entrance check.** ChatGPT's discovery starts from the 401 `WWW-Authenticate` challenge on `/mcp`; the check assumes the well-known path and would stay green if that challenge header regressed. A future bounded assert is worth considering; not needed for this decision.
