
## Shared setup acceptance trace S-1

Status: required future proof, not an executed test. Both companion proposals use
this same trace/version. It extends H-C10/E-C12; passing only those earlier
context/view examples does not complete whole-harness or whole-setup replacement.

Prepare accounts A and B. A publishes a setup inventory containing workflow,
harness and experience source plus pinned dependencies and symbolic resource roles.
B already has conversation C, durable memory M, document D, private bindings B0,
custom component K, preference overlay O, and an active run R. Seed distinct
synthetic private sentinels in both accounts; do not use real credentials as fixtures.
Record source/binding revisions, per-store cursors, memory/content digests and
canonical run/request references in private evidence.

| Step | Operation in B through ordinary user capabilities | Required evidence |
| --- | --- | --- |
| 1 | Import A's setup into private staging | Source and lineage preserved; no activation, schedules, private reads or effects; none of A's private sentinels or grants arrives |
| 2 | Activate only A's UI over B's harness | C/M/D and R remain B's; B0/O are preserved or explicit conflicts are staged; first-party and user paths use the same operation handlers |
| 3 | Keep that UI and replace the actual served harness | New committed turns use selected context, memory, loop, tool and lifecycle strategies; traces identify changed source and runtime adapter; R retains its pinned behavior |
| 4 | Adopt the entire compatible setup, including its workflows | Bind symbolic roles to B's own authorized resources; source selection changes without copying or resetting C/M/D; importing schedules never starts them |
| 5 | Mix A's shared components with B's K and new custom source | Explicit ports/dependency closure validate; edits and O survive; missing required capability blocks only the unsupported activation |
| 6 | A updates/removes a component B customized | Three-way comparison retains B's work and stages a conflict; B can keep or fork the prior working setup |
| 7 | Roll back a compatible selection; revoke a destination; reconnect another device | Private state and completed effects persist; revoked actions fail; per-store freshness is visible; no replay creates new work |
| 8 | Export B's resulting design and inspect every inventoried artifact | Deliberately shared source/customizations travel; C/M/D/B0, private O, run history and both private sentinel sets remain excluded |

For step 3, a context-only replacement is incremental evidence, not completion.
Demonstrate different bounded loop/tool-selection behavior on a frozen task and
evaluator, an authorized memory write surviving a later turn, pending-input
continuation and cancellation with honest effect outcomes. Preserve the same user
and canonical conversation; no privileged first-party shortcut or platform source
patch is permitted during the replacement exercise.

Retaining user data means retaining the user's canonical stores and identifiers.
It does not mean embedding them in the shared package. If a chosen design requires
an incompatible memory schema, retain the active setup and data, report the conflict,
and use a separately supported migration with recovery; never silently reset.
A separately requested private data transfer has its own custody/authority boundary.

Retain command/interaction traces, environment and exact revisions, before/after
state evidence, denial/uncertainty cases, and actual rendered observations.
Report each step independently as passed, failed or unsupported. A browser layout
or simulated notification cannot pass native delivery, earbud or confinement proof.
