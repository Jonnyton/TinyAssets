**C2 — The protected-field invariant is bypassable inside the same handle.**

## Important

**I1 — Ambiguous parameter ownership on both handles.** `write_graph` already carries top-level `name`, `description`, `tags`, `text`, `graph_id`, `idempotency_key`, and `visibility: str = "public"` (`universe_server.py:511-546`). The create discriminator constrains only `branch_id`/`changes_json`/`definition_json`/`idempotency_key`; nothing makes `definition_json` sole authority. `visibility` is the sharp edge — a caller could reach `visibility="private"` outside the DTO gate. Mirror the existing `target="request"` precedent at `universe_server.py:613-619`: reject non-empty `name`/`description`/`tags`/`text`/`graph_id` and `visibility != "public"` in create mode. Separately, `read_graph.limit` defaults to 30 and is shared with `graphs`/`goals`/`runs` (`universe_server.py:436`), so the delta's "default `limit=25`" is unobservable and lowering the shared default would silently change other targets — specify a sentinel (`limit<=0` → 25 for `branches`) or restate as "at most 25 when unset." Same for `tags`/`goal_id`, currently documented as goal filters.

**I2 — Idempotency is incomplete and not atomic with the insert.** No requirement names the reservation store, its uniqueness constraint, retention/TTL, or post-expiry replay behavior. Tasks 3.1/3.2 place the layer "before calling existing branch handlers," but `save_branch_definition` owns its own `_connect` transaction (`daemon_server.py:2344-2420`), so a reservation taken outside it breaks "one branch, one ledger record, one storage commit" on crash — either a reserved key with no branch, or a branch with no reservation. Require a single transaction (add a connection-accepting seam) or specify reconcile-on-replay, and add a task for the table + migration + TTL.

**I3 — "one attribution/ledger record" names a sink that does not exist.** `attribution_credit` is written only in `api/market.py:985`; `_ext_branch_build` appends no ledger, and `_branch_authoring_batch_receipt` is a response payload, not a persisted row. Name a concrete existing record or drop the clause — don't require an invented sink.

**I4 — `published` scope is cross-store, so "bounded" and keyset pagination don't hold as written.** The order key is `branch_definitions.updated_at` but the published predicate lives in a separate `branch_versions` DB, queried per row (`branches.py:583-589`). Filling a 25-row page can scan the whole table. Require a denormalized active-published marker on the branch row (or a declared scan bound with partial-page semantics), and add the task. Related: today `_ext_branch_list` reports `published: True if scope == "published"` regardless of the `published` column — the delta's "publication state" doesn't say which of the two notions is canonical.

**I5 — Keyset stability is claimed against a mutable sort column.** `updated_at` is rewritten on every patch (`daemon_server.py:2413`), so a row edited mid-walk can be skipped or repeated; the scenario covers only ties. Either order on immutable `(created_at DESC, branch_def_id ASC)` or scope the guarantee to rows unmodified during the walk — and make the load fixture assert the scoped version.

**I6 — `query` has no defined match domain.** `BranchListRequestV1.query` is listed with no statement of what it matches or its length bound; the seam offers `name_contains` (name only) and a single `tag`. On a public catalog that is a disclosure decision, not an implementation detail. State it exactly (recommend: case-insensitive substring on `name` only, ≤200 chars, never node bodies/prompts/source), and map plural `tags` onto the seam's single-`tag` filter. No task currently covers `query`/`tags` filter work at all.
