## ADDED Requirements

### Requirement: The reference protocol is version-pinned and side-effect bounded
The reference implementation SHALL accept only explicitly supported schema and registry versions and SHALL fail closed with stable non-echoing error codes for every unsupported or malformed input. Importing the package, loading a registry, validating evidence, recomputing a result, or calling its Python API SHALL NOT execute a workload, contact a network service, inspect arbitrary environment variables, discover provider/model authority, mutate production state, or select a live target.

#### Scenario: Unsupported protocol version is loaded
- **WHEN** a caller supplies an unsupported schema or registry version
- **THEN** the reference implementation returns the stable unsupported-version failure without reading a substrate or writing evidence

#### Scenario: Protocol API validates an offline bundle
- **WHEN** an owner test calls the protocol API with explicitly selected local files and injected facts
- **THEN** it performs only validation, canonical writing, digest verification, universal recomputation, or rollup
- **AND** it cannot drive a scenario adapter or contact a service

#### Scenario: Protocol package is imported
- **WHEN** a test or owner adapter imports the shared package
- **THEN** no filesystem scan, environment dump, process spawn, network call, provider discovery, or workload execution occurs

### Requirement: Registry loading preserves capability ownership and version history
The reference implementation SHALL validate a closed versioned registry whose entries uniquely bind owning capability, scenario identifier and version, applicability, required/optional status, classification justification, substrate requirements, adapter reference, oracle references, fault declaration, and threshold references. It SHALL reject duplicate identities, missing references, or an applicability/required-status downgrade that lacks a new scenario version and justification. Shared blocking-substrate codes SHALL be versioned; owner extensions SHALL use an owner namespace and SHALL NOT redefine a shared code.

#### Scenario: Registry contains a duplicate scenario identity
- **WHEN** two entries have the same owning capability, scenario identifier, and scenario version
- **THEN** registry loading fails before either entry can run or roll up

#### Scenario: Required scenario is downgraded in place
- **WHEN** history-aware publication receives the prior accepted registry and an entry changes required to optional or applicable to inapplicable without a new version, predecessor ref, and justification
- **THEN** registry publication rejects the change

#### Scenario: Registry history input is unavailable
- **WHEN** a non-genesis registry declares a predecessor digest but the prior accepted bytes are not supplied
- **THEN** history-aware publication is unavailable and cannot approve the new registry

#### Scenario: Owner extension collides with a shared blocker
- **WHEN** an owner-namespaced blocking code attempts to redefine a shared code or another owner's namespace
- **THEN** registry loading rejects it without changing the shared registry

### Requirement: V1 wire shapes limits ordering and bundle layout are exact
The reference implementation SHALL support manifest schema `tinyassets.production-load-evidence/v1`, registry schema `tinyassets.production-load-registry/v1`, command registry `tinyassets.production-load-command-registry/v1`, argv schema `tinyassets.production-load-argv-schema/v1`, blocking-code registry `tinyassets.production-load-blockers/v1`, selection `tinyassets.production-load-selection/v1`, pre-traffic gate set `tinyassets.production-load-gate-set/v1`, dispatch attempt set `tinyassets.production-load-dispatch-attempt-set/v1`, dispatch ref set `tinyassets.production-load-dispatch-ref-set/v1`, bundle index `tinyassets.production-load-bundle-index/v1`, aggregate `tinyassets.production-load-aggregate/v1`, validation result `tinyassets.production-load-validation-result/v1`, safety disposition `tinyassets.production-load-safety-disposition/v1`, trust set `tinyassets.production-load-trust-set/v1`, and authenticated receipt `tinyassets.production-load-receipt/v1`. It SHALL use only the closed enums `passed|failed|not_run`, `real|shaped|mock`, `held|violated|unevaluable`, `expected|loss|duplicate|unexplained`, `public|internal|restricted`, `host|private_universe_brain|vault|platform_held`, and `provider_free|requester_byoc|accepted_market`. Identifiers SHALL match `[a-z][a-z0-9_-]{0,127}` and owner blockers SHALL match `owner.<capability>.<code>` with a kebab-case capability and code `[a-z][a-z0-9_]{0,62}`.

A JSON document SHALL be at most 1,048,576 bytes, depth 16, 128 members per object, 10,000 items per array, and 4,096 UTF-8 bytes per string. A registry SHALL contain at most 10,000 entries, a manifest at most 512 artifact leaves, a canonical JSONL event at most 16,384 bytes before its final LF, and an artifact leaf at most 2,147,483,648 bytes. An offline bundle SHALL be at most 1,073,741,824 bytes. A live bundle SHALL be no more than its authenticated authorization cap. Every bundle SHALL remain below the absolute V1 ceiling of 8,589,934,592 bytes. Integers SHALL be in `[-9007199254740991, 9007199254740991]`; counts, times, durations, and sizes SHALL be non-negative.

The registry SHALL contain exactly `registry_version`, `blocking_code_registry_version`, `predecessor_registry_digest`, and `entries`; each entry SHALL contain exactly `owner`, `scenario_id`, `scenario_version`, `predecessor`, `applicability`, `required`, `classification_justification_code`, `substrate_requirements`, `command_refs`, `adapter_ref`, `oracle_refs`, `fault_ref`, `reconciliation_ref`, `threshold_refs`, `baseline_ref`, `custody_mode`, `backend_policy_digest`, and `owner_blocking_codes`. The manifest SHALL contain exactly `schema_version`, `registry_digest`, `command_registry_digest`, `bundle_index_digest`, `run_id`, `scenario_ref`, `verdict`, `reason_code`, `blocking_codes`, `substrate_class`, `started_at_ns`, `ended_at_ns`, `command_id`, `command_version`, `command_argv`, `seed`, `operator_pseudonym`, `environment`, `generator_health`, `artifact_leaves`, `population_results`, `latency_results`, `owner_results`, `authorization_receipt_ref`, `nonce_consumption_receipt_ref`, `operator_opt_in_receipt_ref`, `isolation_receipt_ref`, `network_identity_receipt_ref`, `canary_start_receipt_ref`, `traffic_start_receipt_ref`, `dispatch_receipt_refs`, `traffic_stop_receipt_ref`, `provider_attempt_receipt_ref`, `abort_receipt_ref`, `canary_receipt_ref`, `cleanup_receipt_ref`, `lockout_receipt_ref`, and `supersedes`; nullable fields SHALL be present as JSON `null`.

The following type grammar is normative. Every listed object is closed, every listed field is required even when nullable, `u53` is an integer in `[0,9007199254740991]`, `positive_version` is `u53 >= 1`, `digest` is exactly 64 lowercase hexadecimal characters, `source_revision` is exactly 40 or 64 lowercase hexadecimal characters, `id` uses the V1 identifier grammar, and `result_code` is either an `id` or a valid owner-blocker string. `ref` is exactly `{id:id,version:positive_version,implementation_digest:digest}`. `scenario_ref` is exactly `{owner:id,scenario_id:id,scenario_version:positive_version}`. Arrays stated as sorted SHALL be ASCII-sorted by the named tuple and contain no duplicate tuple.

- **THEN** the typed owner result is `failed` and binds the attempt receipt

- **AND** the full-interval provider-attempt receipt binds the same authority and exclusion digests with zero unauthorized and zero maintainer-authority attempts
- **THEN** those authorized attempts are not a provider-isolation failure
- **AND** the shared kernel still performs no provider dispatch or authority selection

#### Scenario: Provider dispatch uses maintainer or unbound authority
- **WHEN** a provider-attempt receipt records any maintainer-authority or otherwise unauthorized attempt
- **THEN** the complete conforming scenario is `failed` and safety is `failed_locked`

#### Scenario: Zero-attempt receipt is unavailable
- **WHEN** the accepted provider-attempt boundary cannot prove zero dispatch attempts for the run
- **THEN** the provider-free scenario is `not_run` even when the client reports no provider call

#### Scenario: Zero-attempt receipt covers only pre-run time
- **WHEN** a signed zero-attempt receipt ends before authenticated traffic stop or starts after traffic start
- **THEN** it cannot prove provider isolation for the run
- **AND** possible traffic yields null capacity plus `unknown_locked`

### Requirement: Authenticated authorization abort cleanup and lockout receipts are immutable gates
The reference implementation SHALL validate an authenticated host-issued one-run authorization receipt containing the exact V1 claims above. The manifest SHALL pin its authorization digest, the accepted trust set, and an independently authenticated host/control-plane nonce-consumption receipt or append-only ledger witness bound to the authorization digest, run, nonce, and environment. Replay enforcement belongs to that owner authority; the side-effect-free shared kernel SHALL only verify the authenticated consumption evidence and SHALL NOT infer single use from the authorization object alone. The two required opt-ins SHALL be the verified host authorization and a distinct operator-domain `operator_opt_in` receipt binding the deliberate local flag, run, authorization, environment, and operator pseudonym; the owner adapter SHALL NOT synthesize either. The shared kernel SHALL validate trust-set membership/revocation, authentication, expiry, nonce/run binding, registry/environment/cleanup binding, and authenticated owner-supplied DNS/TLS/no-redirect receipts before accepting any traffic evidence; it SHALL NOT resolve a URL, start/stop traffic, perform cleanup, consume a nonce, or enforce lockout.

The reference implementation SHALL also validate authenticated immutable owner-supplied traffic-start, exhaustive dispatch, traffic-stop, full-interval provider-attempt/canary, abort, cleanup, and durable environment-scoped lockout records. Cleanup evidence SHALL bind the accepted reset plan, lease/fence, pre-run witness, commit witness, planned/deleted/preserved/residual counts and digests, post-run independent inventory, and foreign-state stability. Lockout SHALL be a monotonic authenticated sequence: `locked` binds environment, authorization, run, cause, prior state, and persistence witness; `cleared` requires a later sequence, the current locked digest, an authenticated recovery receipt, zero-residue proof, and foreign-state stability. A stale, forged, unchained, or process-local clear SHALL be invalid. Execution belongs to the separately accepted owner adoption change.

#### Scenario: Live authorization is forged expired or replayed
- **WHEN** a proposed live run has an unknown issuer, invalid authentication, expired authorization, reused nonce, or run/registry/environment/cleanup mismatch
- **THEN** validation refuses the traffic evidence before accepting any DNS or network receipt

#### Scenario: Live authorization is incomplete
- **WHEN** a proposed live run lacks authenticated authorization, local opt-in, isolation, envelope, blast radius, abort, canary, or cleanup identities
- **THEN** the run remains `not_run` and no public traffic starts

#### Scenario: Local opt-in is owner synthesized
- **WHEN** the local flag has no authenticated operator-domain receipt distinct from the owner adapter
- **THEN** the pre-traffic gate set is invalid and no traffic evidence is accepted

#### Scenario: Traffic stop or dispatch coverage is incomplete
- **WHEN** possible traffic has no authenticated stop, dispatch refs omit sent attempt events, or provider/canary coverage does not span the start-stop interval
- **THEN** capacity is null/untrusted and safety is `unknown_locked`

#### Scenario: Target URL or network identity does not match authorization
- **WHEN** the owner receipt contains URL credentials or fragments, a redirect, or a DNS address, TLS identity, or environment identity different from the pinned authorization
- **THEN** validation refuses the traffic evidence

#### Scenario: Cleanup receipt finds foreign or residual state
- **WHEN** the owner cleanup receipt records foreign/shared/credential-bearing/obligated mutation or any test-owned residue
- **THEN** a conforming complete bundle reports capacity `failed` and safety `failed_locked`
- **AND** a durable environment-scoped lockout receipt is required before another live run can be accepted

#### Scenario: Cleanup or lockout proof is omitted after traffic
- **WHEN** an authenticated traffic-start receipt exists and stop, interval coverage, cleanup, required abort, or durable lockout-on-failure proof is missing or invalid
- **THEN** the bundle is protocol-invalid and its capacity verdict is null/untrusted
- **AND** the separate safety disposition is `unknown_locked`
- **AND** no later run is accepted until a valid monotonic locked-to-cleared chain proves recovery, zero residue, and foreign-state stability

#### Scenario: Lockout clear is stale forged or process-local
- **WHEN** a clear record omits the current locked digest, has a non-increasing sequence, lacks an authenticated recovery receipt, or cannot prove persistence across owner restart
- **THEN** validation rejects the clear and preserves the assumed locked state

#### Scenario: Owner abort receipt records a post-traffic safety violation
- **WHEN** an owner receipt records an unauthorized or maintainer-authority provider attempt, tenant bleed, envelope breach, declared abort-threshold crossing, foreign mutation, cleanup residue, canary monitor loss, or generator-control loss after traffic began
- **THEN** the typed scenario result is `failed`
- **AND** the abort and cleanup receipts must be present and digest-bound

### Requirement: Traffic-phase verdict transitions are deterministic
Before traffic, missing or stale authorization, real substrate, monitor/canary, fingerprint, isolation, provider-authority receipt boundary, or cleanup authority SHALL evaluate `not_run`. A malformed, noncanonical, tampered, or internally contradictory bundle SHALL be a protocol-validation failure and SHALL NOT be reported as a capacity verdict. With complete authenticated post-traffic evidence, an unauthorized or maintainer-authority provider attempt, tenant bleed, authenticated-envelope breach, abort-threshold crossing, foreign mutation, cleanup residue, required reconciliation loss, canary monitor loss, or generator-control loss SHALL evaluate capacity `failed` and safety `failed_locked` where the event affects the safety boundary. An authorized requester-BYOC or accepted-market attempt matching the bound authority is not itself a failure. Missing required post-traffic proof instead follows the protocol-invalid plus `unknown_locked` rule. Canary unavailability before start SHALL be `not_run`; monitor loss after start SHALL be `failed`.

Generator evidence SHALL include planned/offered and achieved operations, generator queue delay, CPU, memory, network/socket/connection pressure, dropped events, and clock skew. Generator saturation, unachieved offered load, or clock unsynchronization SHALL evaluate `not_run` unless independent retained evidence proves that a required server-side invariant was violated, in which case the scenario SHALL be `failed`. Each owner dispatch receipt SHALL prove that the authenticated request/rate/concurrency/connection/data caps were enforced immediately before dispatch and SHALL state the allowed maximum in-flight overshoot and drain behavior; the shared kernel SHALL validate those fields and SHALL NOT execute dispatch.

#### Scenario: Required gate disappears before traffic
- **WHEN** authorization, substrate, monitor, fingerprint, isolation, provider receipt boundary, or cleanup authority is missing or stale before traffic
- **THEN** the scenario is `not_run`
- **AND** the owner adapter has no accepted dispatch evidence

#### Scenario: Evidence bundle is tampered
- **WHEN** canonical bytes, a digest, a reference, or a typed receipt is malformed or contradictory
- **THEN** protocol validation fails
- **AND** no `passed`, `failed`, or `not_run` capacity claim is synthesized from the invalid bundle

#### Scenario: Generator cannot deliver the declared load
- **WHEN** generator saturation, queueing, dropped events, clock skew, or achieved load invalidates the declared offer
- **THEN** the scenario is `not_run`
- **AND** it is `failed` only if independent retained evidence already proves a required server-side invariant violation

#### Scenario: Safety boundary breaks after traffic begins
- **WHEN** accepted evidence records an unauthorized or maintainer-authority provider attempt, tenant bleed, envelope breach, abort crossing, foreign mutation, residue, required reconciliation loss, canary monitor loss, or generator-control loss after traffic starts
- **THEN** a conforming complete bundle reports capacity `failed`
- **AND** safety is `failed_locked` when the event affects the safety boundary
- **AND** the relevant abort, cleanup, reconciliation, and lockout receipts are digest-bound

### Requirement: Protocol conformance stays separate from capacity evidence
The reference implementation SHALL emit protocol-conformance results separately from scenario and aggregate verdicts. A passing conformance suite SHALL NOT change any real scenario verdict. The Python API SHALL only validate, canonically write, verify, recompute universal math, or roll up explicitly supplied evidence and SHALL NOT execute an adapter. Unavailable PostgreSQL, Realtime, fleet, settlement, fault-control, provider, or connector substrates SHALL remain `not_run` until their owning capability supplies an accepted real or real-equivalent adapter and environment.

#### Scenario: Offline conformance suite passes
- **WHEN** every protocol unit and property test passes while no real production substrate is available
- **THEN** protocol conformance is `passed`
- **AND** every required unavailable production scenario remains `not_run`

#### Scenario: Owner has not adopted the schema
- **WHEN** a capability has no separately accepted adapter and registry entry for the current schema version
- **THEN** the shared implementation does not synthesize a workload, threshold, or capacity verdict for that capability

## MODIFIED Requirements

### Requirement: Live public-surface runs are authorized and isolated
The system SHALL require a production-load run against a live public surface to record explicit host authorization, a declared traffic envelope, blast radius, abort criteria, uptime-canary coordination, isolated test identities, and a cleanup path. Such a run SHALL NOT consume maintainer quota. A provider-invoking path SHALL remain `not_run` unless authorization selects requester BYOC or accepted-market authority and full-interval authenticated attempt evidence proves zero unauthorized and zero maintainer-authority attempts. A valid authenticated cleanup receipt that proves residue or foreign-state mutation SHALL produce a conforming `failed` result and durable lockout. Missing, malformed, unauthenticated, or incomplete cleanup proof after possible traffic SHALL instead make the bundle protocol-invalid, null its capacity verdict, and produce `unknown_locked`; invalid evidence SHALL NOT be normalized into a trusted failure result.

#### Scenario: Connector baseline is authorized
- **WHEN** an operator runs a baseline against canonical `/mcp`
- **THEN** the manifest records authorization, bounded traffic and abort criteria, isolated identity scope, cleanup, and canary coordination

#### Scenario: Candidate flow would invoke a provider
- **WHEN** a proposed live load path would call a model/provider
- **THEN** the production scenario is `not_run` until a provider-free adapter or separately authorized requester-BYOC or accepted-market path exists
- **AND** no user run may consume Jonathan's or any platform maintainer's provider quota

#### Scenario: Valid cleanup evidence proves failure
- **WHEN** an authenticated cleanup receipt proves residue, foreign-state mutation, or failure to clean the isolated test scope
- **THEN** the conforming scenario is `failed`, safety is `failed_locked`, and subsequent live runs remain unauthorized until authenticated recovery clears the lockout

#### Scenario: Cleanup proof is missing or invalid after possible traffic
- **WHEN** traffic may have occurred and the required cleanup or lockout proof is absent, malformed, unauthenticated, or incomplete
- **THEN** protocol validation fails, the capacity verdict is null, and safety is `unknown_locked`
- **AND** no later run is accepted until a valid monotonic recovery chain proves zero residue and foreign-state stability
