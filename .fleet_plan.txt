# Refactor plan

Plan against local `origin/main` at `17bf0de289bd8a2fd1e16fcaa07e4a11629100cd`. The worktree was clean; I made no edits.

The safest shape is a strangler migration:

1. Add a daemon-owned queue consumer that claims work without representing itself as a provider worker.
2. Resolve every provider call through the queued task’s universe assignment and background authority.
3. Cancel the three stale tasks and retire the two stale runtime instances through a fenced reconciliation command.
4. Cut over by activation epoch, then remove the dormant fleet machinery.

Do not cherry-pick the old branch. Its direction was useful, but it synthesized broader permissions than the serving binding granted, bypassed some spend controls, had TOCTOU gaps, and initially mass-cancelled queue rows.

## 2. Replacement execution design

The new execution path should be:

```text
automation admission / v1 compatibility task
              |
              v
daemon-owned AssignedQueueConsumer
  - one bounded consumer inside the existing daemon service
  - scans background-enabled universes
  - claims by activation epoch + immutable task/version + lease CAS
              |
              v
execute_claimed_branch_task(...)
  extracted from fantasy_daemon/__main__.py:1292
              |
              v
authorize_background_served_provider_call(...)
  - exact universe owner
  - current serving assignment
  - background operation/role
  - provider binding + custody generation/digest
  - attempt and budget reservation
              |
              v
per-call credential snapshot -> UniverseBoundProviderCall
              |
              v
execute_branch_version(...) -> terminal receipt/reconciliation
```

### Exact seams

1. Add a daemon-owned runtime such as `AssignedQueueConsumer` and start it from [`universe_server.main`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/universe_server.py:3091), alongside the existing served-budget maintenance. It should be a bounded, stoppable background executor in the daemon process—not another compose service.

2. Extract [`_try_execute_claimed_branch_task`](C:/Users/Jonathan/Projects/wf-exec-capacity/fantasy_daemon/__main__.py:1292) into a neutral callable:

   `execute_claimed_branch_task(base_path, claimed_task, executor_identity, provider_call)`

   Both `fantasy_daemon` and the new consumer call it. Preserve immutable `execute_branch_version` use at lines 1574–1588, cancellation heartbeats, run-ID reservation, terminal receipts, and continuation fencing.

3. Replace the worker-bound call to [`prepare_claimed_cloud_provider_call`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/cloud_automation_continuation.py:2438) with:

   `authorize_background_served_provider_call(base_path, claimed_task, consumer_lease)`

4. That function should reuse the underlying served-provider authority chain, not its interactive request carrier:

   - Current serving selection: [`provider_serving_binding.py:590`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/provider_serving_binding.py:590).
   - Current atomic assignment/custody/snapshot path: [`authorize_served_provider_call`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/provider_assignment.py:1091).
   - Exact-universe call wrapper: [`UniverseBoundProviderCall`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/providers/call.py:91).

   The existing serving grant is explicitly limited to `converse`/`writer` at [`provider_serving_binding.py:49`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/provider_serving_binding.py:49) and [`provider_assignment.py:1155`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/provider_assignment.py:1155). Therefore the implementation must define an explicit background operation such as `background_branch_run`, including allowed branch roles and spend ceilings. It must not manufacture `run_graph` permission from a converse-only grant.

5. Within one authority fence, re-read:

   - task/admission digest and pending/claimed generation;
   - current automation activation epoch and immutable branch version;
   - background binding and attempt;
   - universe owner and current assigned serving provider;
   - provider-work binding generation/digest and credential custody;
   - token/cost/attempt budget.

   Then reserve budget and create the per-call credential snapshot. Always clean the snapshot in `finally`. Rotation, revocation, or authority mismatch should move the attempt to an authority-held/retryable condition—never fall back to ambient credentials or another provider.

6. Generalize worker audience names gradually. Initially, `BackgroundBranchExecutorClass.CLOUD` can remain a persisted compatibility value meaning “platform service executor.” Introduce a process-level `consumer_id`/lease rather than creating a fake Codex or Claude worker runtime.

Add regression tests proving scheduled runs still use the assigned provider, but do not route them through the queue merely to unify code paths.

## 3. Safe stale-artifact reconciliation

Use an on-demand, code-based reconciler. Running it automatically on every boot is too dangerous because `awaiting_compatible_capacity` is derived and will change meaning after cutover.

Proposed command:

```text
python -m tinyassets.runtime_reconcile stale-fleet \
  --older-than-hours 336 \
  --dry-run

python -m tinyassets.runtime_reconcile stale-fleet \
  --older-than-hours 336 \
  --apply \
  --expected-plan-digest <dry-run digest> \
  --expect-task-count 3 \
  --expect-runtime-count 2
```

### Task reconciliation

Add:

- `Epoch2BranchTaskAdapter.plan_stale_capacity_cancellation(...)`
- `RequestAdmissionStore.cancel_pending_v2_task_if_stale(...)`

The planner should select only tasks that:

- are epoch-2 and still `pending`;
- are older than the cutoff;
- classify as `awaiting_compatible_capacity` under the pre-cutover legacy matcher;
- have valid admission/task integrity;
- belong to the retired cloud executor class;
- match the exact dry-run digest.

The apply function performs a `BEGIN IMMEDIATE` CAS and rechecks status, timestamp, generation, and digest. It should use the lifecycle behavior already present in [`request_v2_cancel`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/storage/request_admissions.py:1553): pending tasks become `cancelled`, and the admission/request/task event records are updated. No row or payload is deleted.

Record reason:

`stale_awaiting_compatible_capacity_retired_fleet`

If counts or the plan digest differ from the reviewed dry run, abort the entire apply.

### Runtime reconciliation

Add:

- `daemon_registry.plan_stale_cloud_worker_runtime_retirement(...)`
- `daemon_server.retire_runtime_instance_if_stale(...)`

Select only `author_runtime_instances` that:

- remain `provisioned`;
- carry `metadata.runtime_registration == "cloud_worker"` from [`ensure_daemon_runtime`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/daemon_registry.py:366);
- have an expired descriptor/dead heartbeat beyond the threshold;
- own no current claim or unexpired lease;
- match the dry-run digest and expected `updated_at`.

Use the lifecycle update in [`retire_runtime_instance`](C:/Users/Jonathan/Projects/wf-exec-capacity/tinyassets/daemon_server.py:1331), setting status to `retired`. Do not delete daemon definitions, run history, attribution, or task records.

Run reconciliation after legacy workers are fenced off and before the new consumer is allowed to claim. Otherwise the new capacity model could make the 19-day-old tasks runnable before they are cancelled.

## 5. Principal risks and verification

| Risk | Control and proof |
|---|---|
| Cross-universe credential use | Exact universe/task/assignment/custody checks immediately before every provider launch. Tests with concurrent Codex and Claude universes must prove zero cross-routing and no ambient fallback. |
| Duplicate execution or split brain | Activation epoch plus transactional claim/lease generation. Randomized claim-vs-cancel, two-consumer, lease-expiry, and crash-after-claim tests; exactly one run/attempt/provider reservation. |
| Cost explosion | Durable attempt, token, and cost reservation before subprocess launch. Per-universe and global concurrency caps. Rotation/retry must not mint a fresh budget. |
| Stale cleanup data loss | Dry-run digest, exact expected counts, cutoff, CAS, cancellation events, and retained payload/history. Never `DELETE`. |
| Provider subprocess harms MCP uptime | Bounded background executor; task exceptions cannot kill the HTTP process. Hung calls have leases/timeouts. MCP remains available while execution health reports degraded. |
| Green canary hides broken graphs | `mcp_public_canary --assert-handles` is necessary but insufficient. Execute a real queued immutable branch through the rendered chatbot connector and observe `pending → claimed/running → succeeded`, assigned provider, terminal receipt, and output. |
| Persisted-schema breakage | Retain legacy executor/worker provenance fields initially; add new status fields alongside old fields for one compatibility release. Migrate/remove separately. |
| Unsafe rollback | Worker services stay profile-gated and denied by the deploy fence. A rollback cannot silently recreate provider workers or consume already-cleaned tasks. |
| Host-pool regression | Keep `host_pool` out of this PR unless the founder explicitly retires its current REST contract and provides a Tier-2/market replacement. |

### §14 proof

Before declaring the uptime surface recovered, run a load scenario with multiple consumer loops, thousands of pending tasks, and mixed-provider universes. Acceptance should include:

- zero duplicate terminal executions;
- zero cross-universe or cross-provider credential selections;
- zero unhandled SQLite lock failures;
- cancel-vs-claim and rotation-vs-launch races fail closed;
- expired claims recover exactly once;
- consumer restart leaves no permanent budget reservations;
- bounded provider concurrency and queue latency under the configured limit;
- MCP health and latency remain within budget while queue execution is saturated.

Final live evidence must include the deployed SHA in `release_state`, public canary, a rendered connector conversation, a successful queued run using the universe’s assigned provider, and post-fix clean-use evidence.

  --expect-task-count 3 \

## 5. Principal risks and verification

| Risk | Control and proof |
|---|---|
| Cross-universe credential use | Exact universe/task/assignment/custody checks immediately before every provider launch. Tests with concurrent Codex and Claude universes must prove zero cross-routing and no ambient fallback. |
| Duplicate execution or split brain | Activation epoch plus transactional claim/lease generation. Randomized claim-vs-cancel, two-consumer, lease-expiry, and crash-after-claim tests; exactly one run/attempt/provider reservation. |
| Cost explosion | Durable attempt, token, and cost reservation before subprocess launch. Per-universe and global concurrency caps. Rotation/retry must not mint a fresh budget. |
| Stale cleanup data loss | Dry-run digest, exact expected counts, cutoff, CAS, cancellation events, and retained payload/history. Never `DELETE`. |
| Provider subprocess harms MCP uptime | Bounded background executor; task exceptions cannot kill the HTTP process. Hung calls have leases/timeouts. MCP remains available while execution health reports degraded. |
| Green canary hides broken graphs | `mcp_public_canary --assert-handles` is necessary but insufficient. Execute a real queued immutable branch through the rendered chatbot connector and observe `pending → claimed/running → succeeded`, assigned provider, terminal receipt, and output. |
| Persisted-schema breakage | Retain legacy executor/worker provenance fields initially; add new status fields alongside old fields for one compatibility release. Migrate/remove separately. |
| Unsafe rollback | Worker services stay profile-gated and denied by the deploy fence. A rollback cannot silently recreate provider workers or consume already-cleaned tasks. |
| Host-pool regression | Keep `host_pool` out of this PR unless the founder explicitly retires its current REST contract and provides a Tier-2/market replacement. |

### §14 proof

Before declaring the uptime surface recovered, run a load scenario with multiple consumer loops, thousands of pending tasks, and mixed-provider universes. Acceptance should include:

- zero duplicate terminal executions;
- zero cross-universe or cross-provider credential selections;
- zero unhandled SQLite lock failures;
- cancel-vs-claim and rotation-vs-launch races fail closed;
- expired claims recover exactly once;
- consumer restart leaves no permanent budget reservations;
- bounded provider concurrency and queue latency under the configured limit;
- MCP health and latency remain within budget while queue execution is saturated.

Final live evidence must include the deployed SHA in `release_state`, public canary, a rendered connector conversation, a successful queued run using the universe’s assigned provider, and post-fix clean-use evidence.
